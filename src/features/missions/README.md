# src/features/missions

The mission runtime and runner (md-files/06-mission-system.md): loading mission files from `src/content/missions`, working out which objectives are done, the in-memory run, headless play, and the briefing → workspace → debrief UI. Everything is driven by the mission object: no component, reducer or script names a mission, an objective or a character (`tests/unit/mission-run.test.ts` checks).

- `index.ts` — client-safe:
  - evaluation: `evaluateObjectives(mission, state, events, answers)` (the one pure evaluator: completed objective ids, in objective order), `isMissionComplete`, `mainObjectives`, `missionProgress`, `eventMatches`;
  - the run: `missionRunReducer(mission, run, action)` and `createMissionRun()` (pure), the selectors `currentObjective`, `canAnswer`, `visibleObjectives`, `rewardSummary`, `isRunInProgress`, `failedAttempts` (for the mentor's nudge chip, never a score) and `runMinutes`, and `useMissionRun(mission)`, the one in-memory React store;
  - headless play: `playMission(mission, steps)`, `formatPlaythrough`, `verifyPlaythrough(mission, playthrough)`;
  - Usage counts: `usageEventsBetween(mission, before, after)`, the anonymous events one change to a run produces (ids only; `md-files/metrics.md`).
  - UI: `MissionRunner` (with `links` resolved by the page, and `onStatusChange` for the top bar and the leave guard), `MissionList`, `summarizeMission`, `MissionText`, `DIFFICULTY_LABELS`.
- `server.ts` — server-only (reads files): `getMission(slug)`, `getMissionById(id)`, `listMissions({ skill, difficulty })`, `getMissionGraph()` (the "Best after" graph, never used for locking), `loadMissionCatalog(dir)`, `parseMissionSource`, `MissionSourceError`, and the playthrough loaders `loadPlaythrough(id)`, `loadPlaythroughs()`, `parsePlaythroughSource`. Cached in production, re-read on every call in development.
- `loader/` — `source.ts` checks one file (YAML, schema, id matches the file name, the engine builds the scenario, checks name real hosts, users and flags); `catalog.ts` checks across files (unique ids and slugs, prerequisites exist and don't loop) and orders missions by difficulty, then prerequisites, then title; `playthroughs.ts` reads `src/content/missions/playthroughs`.
- `evaluate.ts` — the evaluator. It reports what holds now; the run keeps the union of ticks, so a tick once earned stays.
- `run/` — `review-facts.ts` (`reviewFactsFor`: the facts the mentor's post-mission review needs, unfound secrets left out), `mission-run.ts` (the reducer: Start mission and the first trip to the debrief record their time from the action, so the reducer stays pure; Start mission plays the `start` beats; each command re-evaluates, keeps every tick, and plays the beats it triggers once each, in the order events → objectives → `complete`; answer objectives open in story order; choices that aren't accepted add their character's reply; secrets queue a toast; the debrief waits for the main objectives), `use-mission-run.ts`, `play.ts` (commands go through the terminal feature's own session code, so headless play matches the browser), `verify.ts`.
- `components/` — `mission-runner.tsx` (the briefing, focus moving to each new screen's heading, the anonymous usage counts, and, on Start mission, `mission-play.tsx` loaded on demand: phase 11 keeps the engine, terminal, map and mentor out of the briefing page's first download, and warms the chunk up while the learner reads), `mission-play.tsx` (everything after Start mission: the terminal session and the mentor session live here, across workspace and debrief), `mission-briefing.tsx`, `mission-workspace.tsx` (team chat, terminal with Explain this, the network map when the scenario has more than one host, objectives, secret toasts, Restart mission, the Reference and the mentor panel taking turns over the side, and the "Want a nudge?" chip), `story-panel.tsx` (the newest batch of lines in full), `objectives-panel.tsx` (why on expand, and the way to the step's free hints in the mentor panel), `answer-input.tsx`, `mission-debrief.tsx` (with the mentor's post-mission review, asked for by the learner), `mission-list.tsx`, `mission-summary.ts`.

Answers for `answer` checks ship with the mission in the client bundle on purpose (improvement #3 in `md-files/00-overview-and-improvements.md`): nothing is recorded, so peeking only spoils the learner's own mission. No mission state is ever written to browser storage: leaving or reloading ends the run, and the app shell asks first while one is in progress (`LeaveGuard`).

Public API: `index.ts`, and `server.ts` for server code. Never import here: another feature's internals, or anything that stores state.
