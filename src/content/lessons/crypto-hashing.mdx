## The one-sentence version

A <Term id="hash">hash</Term> is a short string of characters made from a piece of data, by a recipe that only runs one way.

Picture a blender. Put the same fruit in and you get the same smoothie every time. Swap one grape and the smoothie comes out a different colour. And nobody, however clever, can pour the smoothie back out as fruit.

That last part is the bit that surprises almost everyone, so let's start there. Have a guess — there's no wrong turn here, and the explanations are worth reading either way:

## Why it matters in security

You'll meet hashing in two places on almost every job, and they're worth keeping apart in your head.

The first is **checking nothing changed**. Hash a file today, hash it again next month, and compare the two fingerprints. Same fingerprint, same file, down to the last byte. A different one means something edited it. That's <Term id="integrity">integrity</Term>, and it's why a downloaded program often comes with a hash printed beside it.

The second is **storing passwords without keeping the password**. A shop that stores what you typed has a file that reads like a list of front-door keys. A shop that stores hashes has a list of fingerprints: when you sign in, it hashes what you typed and compares fingerprints. It never needs your password back, so it never keeps it. The next lesson, [How systems store your password](/learn/crypto-password-storage), follows that thread.

## How it actually works

A hash recipe takes data of any size and gives back a fixed number of characters. Three things make one useful, and they're all you need to carry from this lesson:

1. **Same in, same out.** The same input always produces the same hash, on any computer, forever.
2. **Fixed length.** One word and an entire library both come out the same size. The recipe called MD5 gives 32 characters; the one called SHA-256 gives 64. That's why a hash is a fingerprint rather than a summary: it tells you _which_ data, never _what_ the data said.
3. **One direction only.** There is no un-blend button. The only way to find the input behind a hash is to guess an input, hash it, and see whether the fingerprints match. That guessing is called <Term id="password-cracking">password cracking</Term>, and it's why a long password matters: it makes the pile of guesses enormous.

So a hash isn't a lock that someone might pick. It's a shape that can be recognised, and that's all it ever is. If that clicks, the rest of this topic gets much friendlier.

Where the blender analogy stops: a smoothie made from ten grapes looks much like a smoothie made from eleven. Hashes don't work that way. The recipe is designed so that near-identical inputs give fingerprints with nothing in common.

## In practice

In the mission [Reading the machine](/missions/linux-01), you find a password sitting in a configuration file as <Term id="plaintext">plaintext</Term> — the readable form, no fingerprint anywhere. Anyone who could open the file could read it and use it. That's the problem hashing exists to solve, and meeting the plain version first is what makes the fingerprint version feel like a relief.

When you meet a fingerprint on a client's machine, the habit to build is: name the shape, say whether the recipe is a strong one, and write that in the report. That's a genuinely useful finding, and it's one you can already write. If you'd like the full manual page, `man hashid` has it in any terminal here.

## Common misconceptions

If you arrived holding any of these, you're in very good company — they're the ideas almost everyone has to put down on the way in.

- **"A hash can be decrypted."** Websites offering to "decrypt MD5" aren't reversing anything. They hashed millions of common passwords ahead of time and look yours up in that list. If your password isn't in their list, they have nothing — which is also why an unusual passphrase survives and `summer2024` doesn't.
- **"Hashing and encrypting are the same thing."** Encryption is meant to be undone by whoever holds the key. Hashing is meant never to be undone by anyone. [Encryption, and how it differs from hashing](/learn/crypto-encryption-basics) takes that apart properly.
- **"A longer hash means a stronger password."** The length comes from the recipe, not from you. A one-character password hashed with SHA-256 still gives 64 characters, and it still falls in under a second.
- **"Two hashes that start with the same characters mean similar passwords."** Nothing about the input survives. Matching starts are coincidence, and tell an attacker nothing.
- **"If a company hashed the passwords, a break-in doesn't matter."** It matters far less, and that's a real achievement worth giving a company credit for. But fast recipes and common passwords still lose. Turning "far less" into "hardly at all" is exactly where the next lesson picks up.
