## The one-sentence version

When you open a web page, your <Term id="browser">browser</Term> asks a computer for it, and that computer sends it back. The language they use for asking and answering is called <Term id="http">HTTP</Term>, short for HyperText Transfer Protocol.

It works like ordering at a counter. You ask for one thing by name, and you get it back with a short note about how it went. Here's what the asking looks like. Pick each part to see what it's for.

## Why it matters in security

Almost every attack on a website travels inside an HTTP message, and so does almost every defence. If you can read requests and responses, you can see what a website accepts, what it refuses, and what it gives away without meaning to.

Websites often say more than they should: the name and version of their software, notes a developer forgot to delete, pages that were meant to be private. Testers read those details, and so do attackers. Defenders read them first and tidy them up.

## How it actually works

The page's address, its <Term id="url">URL</Term> (Uniform Resource Locator), tells your browser which computer to ask and which page to ask for. The browser sends an <Term id="http-request">HTTP request</Term> to that computer's <Term id="web-server">web server</Term>, usually on port 80.

The web server sends back an <Term id="http-response">HTTP response</Term>. The first line holds a <Term id="status-code">status code</Term>, a three-digit number that says how it went:

| Code  | Means            | Like the counter saying…                |
| ----- | ---------------- | --------------------------------------- |
| `200` | OK               | "Here you go."                          |
| `301` | Moved            | "That's over there now."                |
| `401` | Sign in required | "Staff only. Show me your badge first." |
| `403` | Forbidden        | "Even with a badge, not you."           |
| `404` | Not found        | "We don't have that."                   |
| `500` | Server error     | "Something went wrong back here."       |

Then come headers, lines of detail about the answer, and then the page itself.

<Term id="https">HTTPS</Term> is the same conversation with an S for secure: everything is scrambled
on its way across the network, usually on port 443. That's what the padlock in your browser means.
Where the counter analogy breaks down: at a real counter everyone nearby can hear you. With HTTPS,
only you and the website can read what you said.

## In practice

In missions, `webprobe` is how you look at a website without a browser: the status, the headers, the title and any notes left in the source. In the [sandbox](/sandbox), the small network has a practice web server to try it on.

## Common misconceptions

- **"The padlock means the website is safe."** HTTPS protects the conversation on its way, so nobody in between can read it. It says nothing about whether the site itself is honest. A fake shop can have a padlock too.
- **"A web page is one file."** Most pages are dozens of requests: the page, then its pictures, styles and scripts, each fetched with its own request.
- **"Only browsers speak HTTP."** Phone apps, smart ovens and tools like `webprobe` speak it too. A web server answers whoever asks, so it can't trust that a person with a browser is on the other end.
